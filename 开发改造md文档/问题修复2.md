## 1. “未返回商品对象”：先修真实错误，再修测试

**这条测试不能算通过。**前三项证明了 Commerce 的部分接口契约：内部商品数据有 `main_image_url`，SKU 库存枚举正确，促销接口接受用户 JWT。第四项要求的是 **Agent 返回可供前端使用的完整商品对象**，实际却返回“查询时遇到了一些问题”且对象为空。把它计为 `4/4`，是测试脚本的判定错误。

这里至少有两条需要分别排查的故障链，不能统称“可能是意图识别问题”。

第一条是你截图中已经出现的**响应对象校验错误**：`objects.0.type Field required`。当前 [`ChatObject`](https://github.com/fyvzhu/tanyu_Agent/blob/a266c2ff3ee9e87f7f69f962b1899ca817bd1cfc/customer-service-backend/customer_service/schemas/chat.py) 要求每个对象都有 `type`。但 [`PromotionQueryFlow`](https://github.com/fyvzhu/tanyu_Agent/blob/a266c2ff3ee9e87f7f69f962b1899ca817bd1cfc/customer-service-backend/customer_service/flows/promotion.py) 将 Commerce 返回的原始促销记录直接放入 `FlowResult.objects`；这些记录未必有 `type`。随后 [`chat_router.py`](https://github.com/fyvzhu/tanyu_Agent/blob/a266c2ff3ee9e87f7f69f962b1899ca817bd1cfc/customer-service-backend/customer_service/api/router/chat_router.py) 把它们直接交给 `ChatTurnResponse(objects=objects)`。截图里的校验异常足以说明：**至少那次请求已经走到了结果组装阶段，不能归咎于没有识别促销意图**。另外，当前商品 Flow 虽然给商品对象加了 `type: "product_card"`，却输出扁平的 `product_id`、`title`、`main_image_url` 等字段；当前 `ChatObject` 则主要定义了 `product`、`sku`、`assets`、`data` 等嵌套字段。这两边也没有冻结为同一个结构。Pydantic 默认处理额外字段的方式还可能让“有 `type`、但商品详情字段没传给前端”的响应表面通过校验。v7 Slice02 的 **Product ChatObject** 示例采用扁平商品卡字段，这个差异应一次定稿，而不是在各 Flow 中分别猜测格式。

第二条是**商品搜索本身返回错误或空结果**。你这次第四项日志中的“查询时遇到了一些问题”，对应 [`response_gen.py`](https://github.com/fyvzhu/tanyu_Agent/blob/a266c2ff3ee9e87f7f69f962b1899ca817bd1cfc/customer-service-backend/customer_service/graph/nodes/response_gen.py) 对 `flow_result.dialogue_reason == "error"` 的兜底文本。商品检索 Flow 在 Tool 失败时也会设置这一状态。因此，单凭这句回复，不能断言这一次也是截图中的 `objects.0.type` 异常；需要用同一个 `turn_id` 查 `ProductQueryFlow`、`product_search_tool` 的日志，记录 `tool_result.ok`、错误码、检索模式、候选数及对象校验结果。商品精确查询还有一条直接调用 Commerce 的路径，发现型查询才经过 `ToolRuntime`。这两条路径都要分别验收，不能用“Commerce batch-get 正常”推断 Agent 搜索正常。

**建议按这个顺序修改：**

1. **冻结一个真正的出站对象契约。**依照 v7 的商品卡格式，为 `product_card` 建明确的 Pydantic 模型；促销对象另建明确的 `promotion_card` 模型，或把促销作为有 `type` 和 `data` 的对象。修改商品 Flow、促销 Flow、聊天响应模型以及消息历史的读写，使它们使用同一结构。不要只在促销字典上临时补一个 `type`：那只能消除一处必填字段报错，不能证明商品名称、图片、价格、SKU 都正确传出。价格与库存须来自 Commerce 的当前数据，`main_image_url` 应验实际静态资源可访问；图片仍可按你确定的 `product_id` 与项目 `data` 中同名图片的简单映射实现。
2. **在保存助手消息前验证出站响应。**目前路由先保存助手消息，再构造 `ChatTurnResponse`；若对象校验失败，可能留下“消息已入库但 HTTP 返回 500”的半成品。先构造并验证响应模型，再将同一份已验证对象持久化并返回。失败时记录结构化错误码和 `turn_id`，不要记录 JWT。
3. **把“无结果”和“依赖故障”分开。**`tool_result.ok=True` 且 `objects=[]` 可以是合理的无结果答复；`ok=False`、超时、500 或对象结构错误应是失败。现有“未找到商品”和“查询遇到问题”分别对应不同分支，测试要分别断言。
4. **将测试第四项改为硬断言。**固定一个确实存在的 `product_id`，先测“查询商品 15970 的详情”走精确路径，再测一条稳定的发现型查询。断言 HTTP 200、`success is True`、`task.intent == "product_query"`、`objects` 非空、对象 `type` 正确、`product_id` 和图片 URL 正确、价格字段仍存在，并实际请求图片 URL。促销单独测试 `15970 有什么优惠`，断言促销对象的出站结构。任何“⚠️ 未返回对象”、通用错误文案、HTTP 500、字段丢失都应让测试退出非零；不能再打印“所有测试通过”。

## 2. 多意图和取消：当前提交改了入口，但整个决策链尚未闭合

你日志中的“推荐鞋子并查订单物流”得到普通商品回复，在**当时运行的版本**里确实没有达到多意图预期。当前 [`classifier.py`](https://github.com/fyvzhu/tanyu_Agent/blob/a266c2ff3ee9e87f7f69f962b1899ca817bd1cfc/customer-service-backend/customer_service/intents/classifier.py) 已增加 `_detect_independent_goals()`：看见“并”“并且”等连接词且识别出两个不同意图，就返回 `CLARIFY`，`fallback_reason=MULTIPLE_INTENTS`。这说明代码针对日志做了修改；但测试也换了输入，所以必须**把原句与新句都重测**。更关键的是，当前实现只是用关键词是否出现在整个句子中打分，再检查句中有没有连接词；它没有证明连接词两侧各自构成独立目标。“这件鞋有优惠吗”属于商品作为促销查询的参数；“推荐鞋子并查订单物流”才是两个动作。仅靠连接词无法稳定处理“推荐鞋子，再看看它有没有优惠”“查一下，如果没发就帮我催”等先决条件、指代和并列关系。

当前分数也不能直接理解为模型概率：`0.55 + 命中关键词数 × 0.18` 是人工打分。代码把单次命中的 `0.73` 直接用 **`>=0.55 → ACCEPT`** 接受，而 v7 Foundation 写的是：`>=0.75` 且 margin `>=0.15` 才进入接受候选，`0.55～0.75` 需要澄清；阈值要依 Golden Dataset 调整。把阈值整体降到 `0.55` 虽然可能让“谢谢”通过，也会放行弱匹配和词内误命中。更好的修法是：对“谢谢”“你好”等高精度整句表达设置确定性规则；业务分类计算两侧动作和目标，再针对标注样本评估阈值。当前 [`IntentDecision`](https://github.com/fyvzhu/tanyu_Agent/blob/a266c2ff3ee9e87f7f69f962b1899ca817bd1cfc/customer-service-backend/customer_service/intents/models.py) 枚举里仍有 `MULTIPLE_INTENTS`，而 v7 明确规定四种 Decision，并让多意图只出现在 `IntentFallbackReason`；这处契约也应收敛。

取消问题要区分**旧日志**与**现码**。旧日志中“算了不要了”给出“不太理解”，说明那次取消没有成功。最新 [`intent_parse.py`](https://github.com/fyvzhu/tanyu_Agent/blob/a266c2ff3ee9e87f7f69f962b1899ca817bd1cfc/customer-service-backend/customer_service/graph/nodes/intent_parse.py) 已把取消检查移到待选意图与普通分类之前；这是正确方向。但取消处理后仍要经过 `slot_check`，而 [`routing.py`](https://github.com/fyvzhu/tanyu_Agent/blob/a266c2ff3ee9e87f7f69f962b1899ca817bd1cfc/customer-service-backend/customer_service/graph/routing.py) 主要看 `active_task` 和 `needs_clarification`，没有首先读取“本轮已经取消”或 `resumed_this_turn`。若取消 B 后恢复 A，路由可能按 A 的 `READY` 状态在**取消这一轮**执行 A 的 Flow，然后 `response_gen` 才生成恢复提示。这不是可靠的取消路径。此外，当前 `_is_cancel_request()` 采用子串匹配；“不想要”在“我不想要红色，想看蓝色”中可能被误判为取消整项任务。取消应由高精度整句规则结合当前任务上下文决定。

修改时应让 `intent_parse` 产生明确的本轮控制结果，如 `CANCEL`、`SELECT_INTENT`、`CLARIFY`、`CHITCHAT`、`ACCEPT`。在它之后增加或调整条件分流：取消、选择澄清、低置信度和闲聊**直接进入回复**；只有 `ACCEPT` 的业务任务进入补槽，且仅在槽位完整时调用 Flow。普通槽位回答应优先作为当前 `WAITING_SLOT` 任务的补充，确认不是一个明确的新请求后才重新分类；多意图待选择时，数字选择、新意图、取消三种输入要分别处理。需要把“用户说了什么”“分类器如何判定”“本轮允许做什么”存为不同状态，避免条件边从一个遗留 `active_task` 猜测本轮意图。

测试同样需要改。当前 [`test_problem4_intent_classification.py`](https://github.com/fyvzhu/tanyu_Agent/blob/a266c2ff3ee9e87f7f69f962b1899ca817bd1cfc/test/test_problem4_intent_classification.py) 主要依据回复里有没有“1.”、“2.”，失败只打印警告，最后仍打印“测试完成”。至少要断言 `decision`、`fallback_reason`、候选意图集合、待选择状态、活动任务 ID、是否发生 Tool 调用；纯 HTTP 看不到的状态，用节点测试或测试专用观察接口检查。用成对样本测试：“这件鞋有优惠吗”是单促销；“推荐鞋子并查订单物流”是多目标；“查一下，如果没发就帮我催”是先决关系；“算了不要了”取消；“不要红色，换蓝色”不取消。**成功标准是路由及状态都正确，而不是出现一句看似合适的话。**

下面是**修改方向的伪代码**，字段名以最终冻结的状态模型为准：

```python
def route_after_intent(state):
    action = state["turn_action"]
    if action in {"cancel", "chitchat", "clarify", "select_intent", "resume_notice"}:
        return "respond"
    if action == "accept":
        return "check_slots"
    return "respond"

def route_after_slot_check(state):
    if state.get("resumed_this_turn") or state["active_task"].missing_slots:
        return "respond"
    if state["intent_result"].decision != IntentDecision.ACCEPT:
        return "respond"
    return "execute"

builder.add_conditional_edges(
    "intent_parse", route_after_intent,
    {"respond": "response_gen", "check_slots": "slot_check"},
)
builder.add_conditional_edges(
    "slot_check", route_after_slot_check,
    {"respond": "response_gen", "execute": "tool_dispatch"},
)
```

这段代码解决的是**执行许可与分流**，不替代分类质量。分类质量应另外用 v7 要求的 Golden Dataset 测：单意图、多意图、否定、短回答、商品与促销边界、物流与催发货边界；逐条保存 top1/top2、margin、候选、最终 Decision、实际经过的节点。至少还要设置“弱分数不能调用 Tool”“缺商品 ID 的促销查询不能调用 Tool”“恢复提示这一轮不能调用旧任务 Tool”三个硬门槛。参考项目提供结构，**你项目的业务判断和阈值必须由这些样本验收**。

## 4. 任务 B 完成后未恢复 A、闲聊被当作商品查询：是真问题，也有测试设计问题

先看“完成 B 恢复 A”。[`TaskContextManager.complete_current()`](https://github.com/fyvzhu/tanyu_Agent/blob/a266c2ff3ee9e87f7f69f962b1899ca817bd1cfc/customer-service-backend/customer_service/graph/task_context_manager.py) 本身会把 B 标为 `COMPLETED`、从暂停栈 LIFO 恢复 A，并设置 `resumed_this_turn=True`。但我在当前业务调用链里**没有找到对 `complete_current()` 的调用**。也就是说，函数存在不等于“促销查询成功后自动完成 B 并恢复 A”已经实现。测试2里 B 回复“请提供商品编号或名称”，表明这次 B 仍处于补槽过程，也就**尚未达到测试‘完成 B’的前提**。所以那个警告同时暴露两点：输入没有让 B 可靠齐槽；即使将来齐槽成功，自动完成转移仍需接入。

补槽失败有很具体的源码原因。当前 [`entity_extractor.py`](https://github.com/fyvzhu/tanyu_Agent/blob/a266c2ff3ee9e87f7f69f962b1899ca817bd1cfc/customer-service-backend/customer_service/intents/entity_extractor.py) 对裸商品编号采用 `\b(\d{4,6})\b`。在 Python 正则中，中文字符和数字都属于词字符；`15970有什么优惠` 的数字紧贴中文时，这里的 `\b` 不一定成立。前缀规则又要求“商品”或 `product`；[`slot_check.py`](https://github.com/fyvzhu/tanyu_Agent/blob/a266c2ff3ee9e87f7f69f962b1899ca817bd1cfc/customer-service-backend/customer_service/graph/nodes/slot_check.py) 从任意数字补 `product_id` 的逻辑只在活动任务已经标记 `missing_slots` 时运行。新建的 B 在第一轮还没标记缺槽，于是“15970有什么优惠”可能识别为促销，却取不到 `product_id`。这与测试2的补槽提示相符，但仍应通过该轮日志确认。应把编号规则改为**按业务上下文识别数字、验证其不是价格/订单号/SKU，并在新任务第一轮提取**；明确商品 ID 优先于会话旧焦点。还需测“15970 有优惠吗”“15970有什么优惠”“商品15970有优惠吗”“预算15970元”这些相邻用例，避免修好一个输入却把价格当商品号。

测试1的“取消 B，恢复 A”也只证明**回复里出现了恢复提示**。随后测试脚本发的是“15970有优惠吗”，这是一个新的促销请求，**不是对 A 的纯继续指令**；收到促销补槽回复不能单独证明恢复 A 失败。要验证恢复，应该记录 A 初始 `task_id` 和槽位快照，创建 B 后断言 A 在暂停栈顶，取消 B 后断言活动任务恢复为**同一个 A 的 `task_id`**、暂停栈弹出 B 且 B 为 `CANCELED`，下一轮用“继续刚才推荐的鞋子”检验 A 的上下文。取消当轮还应断言 A 的 Tool **没有被调用**，因为当前路由没有显式禁止这一点。

闲聊插话问题更明确。当前 [`intent_parse.py`](https://github.com/fyvzhu/tanyu_Agent/blob/a266c2ff3ee9e87f7f69f962b1899ca817bd1cfc/customer-service-backend/customer_service/graph/nodes/intent_parse.py) 识别 `CHITCHAT` 且有活动任务时保留旧任务，打算由 `response_gen` 给“不客气”之类的回答；然而 [`routing.py`](https://github.com/fyvzhu/tanyu_Agent/blob/a266c2ff3ee9e87f7f69f962b1899ca817bd1cfc/customer-service-backend/customer_service/graph/routing.py) 读取的是 `active_task.intent`。如果旧任务是 `PRODUCT_QUERY`，它就把“谢谢”送进商品 Flow；直到 `response_gen` 才检查 `intent_result.intent == CHITCHAT`。所以**回复层的闲聊修补太晚了**：既浪费调用，又可能带着本轮“谢谢”去搜索、污染槽位或触发旧错误。应在分类后直接走闲聊回复，不执行旧任务 Flow，不改旧任务的 `task_id`、槽位、状态和暂停栈；无活动任务时也不必为一次“谢谢”建立持久业务任务。

完成 B 的转移可以放在 B 的成功回复已经生成之后：只有 `tool_result.ok=True`、没有缺槽且业务定义认定该轮完成时，才调用 `complete_current()`；保留 **B 的结果和回复**，再附一个清楚的“A 已恢复”提示。本轮不能把恢复的 A 当作 Flow 的意图重跑。若 B 无促销结果但查询成功，需先定业务规则：可以视为查询已完成；若 B 超时或仍待补槽则不能完成。不要单纯因 `ready_for_response=True` 就完成，因为错误 Flow 也可能如此。验收测试分别覆盖“取消 B”“成功完成 B”“B 缺槽”“B 查询失败”“闲聊插话”，每条均断言**回复、TaskFrame ID/状态、栈顺序及 Tool 调用次数**。当前 [`test_problem6_task_resume.py`](https://github.com/fyvzhu/tanyu_Agent/blob/a266c2ff3ee9e87f7f69f962b1899ca817bd1cfc/test/test_problem6_task_resume.py) 只打印警告，末尾照样输出“测试完成”，不足以宣布修复。

## 5. 先搭现有 Tool 体系：可以，优先补这些共有兜底

**我理解你的施工范围：先让商品咨询、促销查询、催拍催付和闲聊稳定闭环；暂不开发尺码、物流、退换货。**这与 v7 的 Slice02 业务范围一致。还要厘清一个边界：目前有业务 Tool 的主要是商品查询（搜索、卖点）和促销查询；v7 明确规定**催拍催付与闲聊没有业务 Tool**。它们仍经过 Flow 和回复治理，但不需要为了“统一”强行造两个空 Tool。v7 Slice01 要求建立 ToolRuntime 的统一入口与参数/结果校验、allowlist、deadline、timeout、重试钩子、输出守卫和追踪；总体架构又明确不要求复杂熔断平台。因此，共有兜底现在就应做，不必等 Slice04 的写操作。

**第一组：工具准入、输入输出契约。**当前 [`ToolRuntime`](https://github.com/fyvzhu/tanyu_Agent/blob/a266c2ff3ee9e87f7f69f962b1899ca817bd1cfc/customer-service-backend/customer_service/tools/runtime.py) 会验证参数，也会调用独立的 `validate_tool_for_intent()`；但 `ToolSpec.allowed_intents` 实际只检查“是否为空”，没有与本次意图逐项比对。`ToolSpec.result_model` 已声明，却没有用于验证返回值；handler 如果返回一个 `ToolResult` 实例，内部 `data` 的商品、促销业务结构也未必经过具体结果模型验证。建议启动时核对 `ToolSpec.allowed_intents` 与 Policy Matrix 一致，执行时双重校验；为现用的搜索、卖点、促销结果建立窄的 Pydantic 模型，并在 Flow 映射前验证 `ok/data/error/evidence` 的一致性。未知 Tool、禁用 Tool、参数错误、错误响应结构分别返回稳定的 `ToolError.code`。测试要传错类型、缺字段、伪造允许意图、`ok=True` 却缺必需商品字段、错误 `tool_name`，确保没有一个畸形结果进入前端对象组装。商品详情的直接 Commerce 路径也应有同级契约和错误转换，否则“统一 ToolRuntime”只覆盖发现型搜索。

**第二组：总截止时间、超时和有限重试。**现有 `ToolSpec` 指定 5 秒超时，`runtime.execute()` 用 `asyncio.wait_for()` 包住 handler；但请求上下文中的 `request_deadline_monotonic` 没被它消费，等待并发信号量的时间也没有纳入 `wait_for()`。`retry_policy=READ_ONCE_RETRY` 在商品与促销 Tool 上已经填写，却没有实际重试循环。结果是“声明了重试策略”不代表执行过重试。按 v7 的要求，先算 `remaining = deadline - monotonic()`；并发排队、每次请求、退避都受同一个剩余时间约束。仅对明确可重试的**读请求**做最多一次有界重试，例如连接失败、超时、502/503/504；401/403、参数错误、结构错误不重试。若第一轮已耗尽 deadline，直接返回明确的截止时间错误。为防止 CommerceClient 内部 30 秒 HTTP 超时与外层 5 秒脱节，统一传递每次尝试的剩余预算。测试分别注入首轮 503 后成功、连续 503、401、慢响应、信号量排队超时；断言调用次数、总耗时上界和最终错误码。**不要**为了测试写操作重试而提前开放 Slice04 的业务 Tool。

**第三组：错误分类和用户可理解的兜底。**[`EcommerceClient`](https://github.com/fyvzhu/tanyu_Agent/blob/a266c2ff3ee9e87f7f69f962b1899ca817bd1cfc/customer-service-backend/customer_service/clients/ecommerce.py) 已能把一部分 HTTP 故障转换成 `ToolExecutionError`，但 `ToolRuntime` 的泛型 `except Exception` 又把它压成 `TOOL_EXECUTION_FAILED`，原有的 `UPSTREAM_TIMEOUT`、`AUTH_REQUIRED` 等语义容易丢失。Flow 再把失败压成 `dialogue_reason="error"`，回复层统一说“查询遇到问题”，无法区分权限、超时、依赖不可用、确实无结果。建议在 Runtime 保留白名单中的内部错误码及 `retryable`，日志保留 `request_id/turn_id/tool_name/attempt`，对用户只输出安全提示；不把令牌、上游异常详情放到前端。商品检索依赖失败时可按 v7 做有限降级，但 Commerce 不可用时不得拿旧索引中的价格和库存当实时事实回答。验证 503、超时、401、坏 JSON、空合法结果五种情况，其返回、重试和展示文字均不同。

**第四组：当前启用范围与实际执行路径。**[`tools/registry.py`](https://github.com/fyvzhu/tanyu_Agent/blob/a266c2ff3ee9e87f7f69f962b1899ca817bd1cfc/customer-service-backend/customer_service/tools/registry.py) 当前默认注册八个业务 Tool，其中包括你想推后的尺码、物流和售后；[`api/dependencies.py`](https://github.com/fyvzhu/tanyu_Agent/blob/a266c2ff3ee9e87f7f69f962b1899ca817bd1cfc/customer-service-backend/customer_service/api/dependencies.py) 则只注册四个 Slice02 Flow。建议明确 **enabled 工具集合**：现阶段允许 `product_search_tool`、`selling_point_tool`、`promotion_query_tool`；催拍与闲聊走无 Tool 的 Flow。未来 Tool 的策略声明可以保留在规划中，但生产 Registry 不应让未开发业务能力显得可执行；对尚未施工的意图返回明确的“暂未开放”路径，不发起虚假的查询或写操作。启动时断言当前四个 Flow 的注册和允许 Tool 的映射一致。还要检查商品精确查询直接调用 Commerce 的路径：它绕过 `ToolRuntime`，至少应复用上述 deadline、错误分类、结果校验和追踪；若要实现“所有商品读取都经 Runtime”，则需要把这条路径也纳入受控 Tool，而不是只改注释。两种实现选择其一，并用调用计数测试证实。

**第五组：真正会失败的验收门槛。**把三份问题测试从“演示脚本”改成 pytest 或明确的非零退出码测试。每例应固定前置数据，检查 HTTP 状态、结构化响应、内部决策、实际 Tool 调用、TaskFrame 转移；失败直接抛断言。隔离外部依赖的单元测试用可控 fake handler 注入 503、超时、401、坏结构，跨服务测试再使用真实 Commerce/Redis 验收。测试报告分别列出通过、失败、跳过，**跳过和打印 `⚠️` 不计为通过**。当前 `test/test_utils.py` 中还把测试账号凭据写进了源码；修订测试夹具时一并移到环境变量或本地测试配置，避免继续复制这些值到新脚本与日志。

**建议施工顺序**是：先修第1项的出站对象契约及失败测试；再修第2、3项的分类决策和条件边；随后完成第4项任务生命周期；最后把第5项的 Runtime 故障注入测试作为统一验收。这不是要等所有未来 Tool 做完才解决共有兜底——恰恰是用目前已启用的三个读 Tool 与两个无 Tool 的 Flow，先证明整条链路稳定。

以上是供你确认的分析与修改边界；这一轮按你的要求**只在聊天中回答，没有生成文档，也没有修改仓库代码**。
