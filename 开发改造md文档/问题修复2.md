# 二十四、Product 的 P0-01 只能算“局部修过”，不能算完整关闭

Codex 之前说：

> Context Resolver 需要更详细需求分析

你后来提供的 MD 其实已经足够详细了。

现在 ContextResolver / QueryPlanner 确实比之前进步了，例如已经区分：

```
```

```
explicit product
discovery
anaphora
ambiguous
```

所以**我不认为文档思路不清楚。**

真正的问题是：

> Codex 修改了 Resolver 本身，却没有把它与真正多轮 State / Focus / Candidate lifecycle 一起打通。

举个最典型的：

```
```

```
第一轮：
“帮我推荐运动鞋”
→ candidates = A/B/C

第二轮：
“第一款有黑色吗？”
```

需要依赖：

```
```

```
候选顺序持久化
   +
conversation_focus
   +
checkpoint
   +
ordinal mapping
```

但当前 Router 重置 Persistent 字段、Flow 又没有稳定把候选结果写回 task/focus。

因此 P0-01 的核心不是再堆 if/else，而应该变成：

```
```

```
Current message semantics
        ↓
ContextResolver
        ↓
QueryContext
        ↓
QueryPlanner
        ↓
Exact / Discovery / Clarify
        ↓
执行结果
        ↓
更新 active_task.slots.candidates / conversation_focus
        ↓
Redis checkpoint
```

这一整环闭上才叫完成。

四十三、索引签名漏掉了实际写入的尺码文本【P1】。 Chunker 会把 size_summary 建成 chunk，但 compute_source_hash() 没包含该字段。修好 Manifest 后，尺码摘要变化仍可能被判为“无需重建”。哈希应覆盖所有会改变索引文本的稳定字段。

四十四、当前 RRF 会让拥有更多命中 chunk 的商品重复加分【P1】。 在线 _rrf() 对候选列表的每一条命中按 product_id 加分；一个商品的多个 chunk 可以在同一来源重复出现。v7 要求先处理 chunk 命中，再聚合到商品级，避免 chunk 数量造成天然优势。应为同一来源、同一商品先去重或聚合，再做跨来源融合。

四十五、Adaptive Retrieval 的 Stage 2 仍没有接到在线执行链【P1】。 代码有 MultiQueryRewriter 和 HyDEGenerator，配置也定义了候选阈值和开关，但当前 ProductRetrievalService.retrieve() 只执行一次 Qdrant + ES + RRF。应在 Commerce 真值过滤后判断有效候选数，不足且功能启用时才执行 Multi-query；HyDE 保持默认关闭。现有策略类若不接线，应明确标为未启用，避免误认为功能已完成。

Foundation 与响应链的补充问题

四十六、ToolRuntime 声明了保护能力，但关键钩子未执行【P1】。 ToolSpec/ToolRuntime 定义了 allowed_intents、retry_policy、result_model、side_effect，实际执行主要做全局意图检查、参数校验、超时和一次 handler 调用；没有使用每个 Spec 的 allowlist、结果模型、重试策略，也没有调用已有的 ActionGuard。这与 Slice01 要求的统一 ToolRuntime 骨架不符。先把实际要支持的钩子接入，再删除无效配置字段；副作用工具将来不能仅靠 side_effect=True 标记。

四十七、Hallucination Guard 没有跟随新 FlowResult 契约更新【P1】。 Guard 仍按旧 dict 格式从 tool_result.products 或 data.items 找证据，而新契约是 FlowResult → ToolResult → evidence/data。此外，路由 读取 guard_status，Guard 节点却主要写 hallucination_detected，未设置对应状态。修复前面第三十八点所涉及的 Flow/Response 主链时，必须同步修复 Guard 的证据输入和路由状态，否则“响应生成成功”不代表 Grounding 已有效检查。

四十八、闲聊没有实现 Slice02 要求的“业务任务中短暂插话”行为【P1】。 Intent Parse 在当前任务与新意图不同时调用 start_task()；TaskContextManager 会把原任务压栈。闲聊又在路由直接绕开 ChitchatFlow。v7 要求用户在补槽过程中说“谢谢”等简短闲聊时，回复后保留原 active task，不 push 闲聊 Task。应补这条专门的任务转换规则和多轮测试。

四十九、Turn Lock 的锁 TTL 与等待方式不符合 Slice01 的并发语义【P1】。 get_turn_lock() 把 checkpoint 的 24 小时 TTL 传给锁；acquire() 默认等待 30 秒。进程在持锁期间退出，锁可能长时间不释放；第二个并发 Turn 通常也会等待，而非按文档立即返回 409 TURN_IN_PROGRESS。锁应有独立的短 TTL、长请求续租策略和明确的冲突响应。

五十、Agent 8000 尚未实现 Request-ID 的 HTTP 契约【P1】。 Agent 应用 没有对应中间件，异常响应固定 request_id: None；EcommerceClient._request() 也没有传播当前请求 ID。07 Contract 要求 8000 读取或生成 ID、响应头回写，并向 8001 传递同一个 ID。这会直接影响两服务错误追踪。

五十一、Agent Readiness 可能在关键能力不可用时仍报告可用【P1】。 /health/ready 将 LLM 标为 not_checked，对 Commerce 只访问 /health/live，且没有报告 Qdrant、ES、Embedding 的降级状态。Slice01 将 LLM 和 Commerce 列为关键依赖，将检索组件列为可降级但须在详情中呈现。应按实际业务可用性区分 ready、degraded 和 unavailable。

全链路测试前应处理的仓库问题

五十二、当前 Compose 不能单靠 docker compose up 启动你描述的全链路【测试阻断】。 docker/docker-compose.yml 的 Embedding 服务被注释，服务清单中也没有 Commerce 8001 和 Agent 8000。你可以用 Compose 启基础设施、再单独启动两个后端，但这种方式要明确写成可重复的启动步骤；若验收目标是“一条 Compose 命令拉起全链路”，就需要补齐服务、健康依赖和环境配置。Qdrant/ES 容器健康本身不能证明 Discovery 路径可用。

五十三、公开仓库中存在可直接复用的默认连接凭据与带密码的用户数据文件【需尽快核实】。 两个后端的配置默认值、Commerce 配置、Compose 都包含固定凭据；仓库还跟踪了 data/users.csv，其表头含 password。如果它们只用于完全隔离的模拟环境，需明确禁止复用；如果任何值仍用于可访问环境，应轮换，并改为由环境注入。我没有在这里重复列出这些值。
