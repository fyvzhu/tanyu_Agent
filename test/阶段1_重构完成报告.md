### Step 3: 重构 intent_parse 节点 ✅
**文件**: `customer-service-backend/customer_service/graph/nodes/intent_parse.py`

**原架构**（单层）：
```
分类器 → 直接设置 turn_action
```

**新架构**（三层）：
```
分类器 → IntentClassificationResult
   ↓
验证器 → TurnDecision
   ↓
执行器 → 设置 turn_action + 状态
```

**核心逻辑**：
```python
# 第1层：分类器
classifier = IntentClassifier()
old_result = classifier.classify(current_message)

# 第2层：适配器
classification = adapt_intent_result_to_classification(old_result, current_message)

# 第3层：验证器
validator = IntentDecisionValidator()
decision = validator.validate(state, classification)

# 根据 decision.action 设置状态
state["turn_action"] = decision.action
```

**处理的 TurnAction**：
- `CLASSIFIER_FAILURE` → 分类器失败
- `OUT_OF_SCOPE` → 超出范围
- `CLARIFY` → 低置信度
- `SELECT_INTENT` → 多目标选择
- `UNSUPPORTED` → 功能未开放
- `CHITCHAT` → 闲聊（不启动任务）
- `ACCEPT` → 接受并启动任务

## 💡 关键设计决策

1. **为什么保留 IntentResult？**
   - 兼容性：其他节点仍依赖 `state["intent_result"]`
   - 渐进式：避免一次性修改所有代码

2. **为什么适配器在分类器文件？**
   - 就近原则：适配器紧贴分类器实现
   - 未来替换：LLM分类器可直接输出新格式

3. **为什么验证器不依赖 TaskFrame？**
   - 解耦：验证规则独立于任务状态
   - 可测：纯函数，易于单元测试
